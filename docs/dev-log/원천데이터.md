> 사실 기반으로 작성되었으며, 필요에 따라 간략화·풀어쓰기 등 형식만 변환한다.

## 기술적 도전 및 해결

### A. 동시성 제어 및 데이터 정합성

#### A-1. 스트릭(Streak) Race Condition — 낙관적 락 + 재시도

**상황**
- 스트릭 업데이트는 문제 제출 시 `SubmissionCompletedEvent` → 비동기 핸들러가 처리
- 사용자가 제출 버튼을 짧은 시간에 중복 클릭하거나 비동기 핸들러가 동시에 실행되면 같은 streak 레코드를 동시에 읽어 각각 `+1` 저장 → 스트릭이 한 번에 2 증가하는 데이터 오염 발생
- 이벤트 기반 구조에서 `@EventListener`는 트랜잭션 커밋 이전에도 발행 가능 → DB 반영 실패 후 스트릭 이벤트가 실행되는 불일치 케이스 존재

**해결**
- **낙관적 락(`@Version`)**: Streak 엔티티에 적용. 충돌 시 `OptimisticLockException` 발생으로 감지. 비관적 락 대비 평상시 성능 저하 없이 충돌 시에만 처리 비용 발생
- **`@Retryable` + 지수 백오프**: 초기 100ms, 최대 3회 재시도로 최종 정합성 확보. "타이밍 문제"이므로 완전 실패보다 재시도가 적절
- **`@TransactionalEventListener(AFTER_COMMIT)`**: 이벤트 수신 시점을 "DB 커밋 완료 이후"로 고정 → 'Submission 저장 실패 후 이벤트 발행'으로 인한 불일치 원천 차단

---

#### A-2. 회원 학습 설정 추가 — TOCTOU Race Condition → 비관적 락

**상황**
- 학습 설정 최대 5개 제한: `count 조회 → 검증 → save` 흐름
- 두 요청이 동시에 진입하면 둘 다 `count=4`를 읽고 검증 통과 → 각각 저장 → 최대 6개 등록
- MySQL Repeatable Read 격리 수준에서 아직 커밋되지 않은 INSERT가 보이지 않아 발생

**해결 방안 비교**

| 방안 | 결정 | 이유 |
|------|------|------|
| `synchronized` | 미채택 | 단일 인스턴스에서만 유효, 멀티 인스턴스 무용 |
| Redis 분산 락 | 미채택 | 외부 인프라 의존, 장애 전파 위험 |
| **비관적 락** | **채택** | DB 레벨 해결, Member row 단위 락이라 다른 회원 간 블로킹 없음 |

**결과**: `appendPreference()` 진입 시 Member row에 `SELECT ... FOR UPDATE` → 같은 회원의 동시 요청만 직렬화. 트랜잭션 범위가 짧아 락 점유 시간 최소화

---

#### A-3. 비동기 문제 생성 + 캐시 정합성 — 커밋 이후 무효화 전략

**상황**
- 카테고리 추가 후 초기 문제를 비동기 생성하는 구간에서 `todayProblem` 캐시에 stale 데이터(빈 리스트 또는 기존 목록) 고착
- `@Cacheable` 기본 동작으로 빈 리스트(`[]`)도 캐시되는 Negative Cache 문제
- 비동기(`@Async`) + 별도 트랜잭션(`REQUIRES_NEW`)으로 생성/조회 타이밍이 엇갈려 stale re-cache 가능
- 조회 키(`memberId:date`)와 무효화 키 식 불일치 시 무효화 누락 위험

**해결**
- `getTodayProblem`에 `unless = "#result == null || #result.isEmpty()"` 적용 → 빈 결과 캐시 방지
- `@CacheEvict` 키를 `#member.id + ':' + T(java.time.LocalDate).now()`로 보정 → 조회 키와 정확히 일치
- 트랜잭션 커밋 이후 무효화 보장 원칙으로 타이밍 레이스 윈도우 축소

### B. 성능 테스트 기반 다단계 병목 진단 및 최적화

**배경**: k6로 최대 400 VU 스트레스 테스트 수행 → Prometheus에서 HikariCP Pending 97건, 응답 지연 급증 관찰. 병목이 한 곳이 아닌 여러 레이어에 중첩되어 있었음.

#### 1단계 — DB 커넥션 풀 고갈 (HikariCP 튜닝)

- **원인**: Spring Boot 기본값(10)으로 방치된 풀 사이즈. 400 VU 동시 요청에 10슬롯은 부족
- **해결**: `(core_count * 2) + effective_spindle_count` 공식 참고, vCPU 2 기준으로 50으로 설정
- **결과**: Pending 수치 급감

#### 2단계 — Slow Query 제거 (복합 인덱스 + Fetch Join)

- **원인**: `DailyProblem` 조회 시 `member_id` + `assigned_at` 조건 JOIN에 인덱스 없어 Full Scan, N+1 문제
- **해결**: 복합 인덱스 `(member_id, assigned_at)` 추가, Fetch Join으로 N+1 제거
- **결과**: **138ms → 30ms 미만 (70% 이상 개선)**

#### 3단계 — 반복 DB 조회 제거 (Caffeine Cache 도입)

**왜 Redis가 아닌 Caffeine인가?**
- 현재 단일 인스턴스 운영 → 분산 캐시 불필요
- Caffeine은 JVM 내부 인메모리 → 네트워크 왕복 없이 나노초 수준 응답
- 향후 멀티 인스턴스 확장 시 Redis로 전환하면 됨

**캐시 설계**

| 캐시 이름 | TTL 전략 | 무효화 트리거 | Max Size |
|-----------|---------|-------------|---------|
| `todayProblem` | 자정 일괄 만료 (커스텀 `Expiry`) | 문제 제출 시 즉시 `@CacheEvict` | 5,000 |
| `streak` | 30분 TTL | 스트릭 증가 시 즉시 `@CacheEvict` | 5,000 |
| `dailyProblemDetail` | 5분 TTL | 문제 제출 시 즉시 `@CacheEvict` | 15,000 |

**캐시 키 설계**: `todayProblem`은 `memberId:date` 복합 키. 날짜가 바뀌면 새 키로 자동 캐싱 → 전날·오늘 캐시 동시 점유(이중 점유) 방지

**캐시 테스트 전략**: `@Cacheable`은 Spring AOP 프록시를 통해 동작하므로 `@InjectMocks` 단위 테스트로는 캐시 동작 검증 불가 → 통합 테스트(`IntegrationTestSupport`)로 검증
- 동일 키 2회 조회 시 DB 1번만 호출 확인
- 회원 간 캐시 독립성 확인
- 쓰기 후 캐시 즉시 무효화 및 재조회 시 DB 재호출 확인

**모니터링**: `CaffeineCacheMetrics`를 Prometheus `MeterRegistry`에 바인딩 → 히트율·미스율·적재 건수 Grafana 실시간 확인

### C. AI 연동 안정성 및 응답 지연 처리

**상황**
- Gemini API 평균 응답 시간 2~5초. 동기 처리 시 HTTP 스레드 점유 + 사용자 블로킹
- 단일 스레드풀에서 AI 호출과 이벤트 처리가 공존 → AI 호출이 큐를 채워 가벼운 이벤트(스트릭 업데이트)조차 지연

**해결**
- **목적별 스레드풀 분리**: AI 호출용 `aiTaskExecutor` + 이벤트 처리용 `eventTaskExecutor` 독립 구성. 장애 격리(Bulkhead) 패턴을 코드 레벨에서 구현
- **비동기 처리(`@Async`)**: 문제 생성을 백그라운드 처리. 사용자는 즉시 응답 수신
- **Fallback 전략**: AI 장애·타임아웃 시 백업 문제 즉시 할당 → 서비스 가용성이 AI API 가용성에 종속되지 않도록
- **AI 자동 채점**: `SubmissionCompletedEvent` 재활용 → `FeedbackEventHandler`가 비동기로 채점 트리거. `Submission:SubmissionFeedback = 1:N`으로 설계, 수정 제출마다 채점 이력 누적

### D. AI 모델 선택 — Gemini vs OpenAI, 환경별 분리 전략

**실측 비교**

| 항목 | OpenAI GPT-5.4-mini | Gemini 2.5 Flash |
|-----|---------------------|--------------|
| 문제 생성 응답 | 약 6.5초              | 약 17초        |
| AI 채점 응답 | 약 4.1초              | 약 10초        |
| RPM | 500                 | 5            |
| RPD (무료) | -                   | 20           |
| 비용 | 유료                  | 무료 플랜 존재     |

**핵심 인사이트**: 두 기능의 지연 허용 범위가 다르다
- **문제 생성**: 자정 배치 + 비동기 처리. 사용자가 즉각 결과를 기다리지 않아 응답 속도가 UX에 직접 영향 없음
- **AI 채점**: 제출 직후 사용자가 피드백을 바로 확인하려 함. Gemini 10초는 GPT 대비 2.4배 느림 → 체감 차이 명확

**결정 — 환경별 모델 분리**

| 환경 | 모델                    | 이유 |
|------|-----------------------|------|
| local / test / staging | Gemini 2.5 Flash (무료) | 기능 동작 검증 목적, 속도보다 비용 절감 우선 |
| production | OpenAI GPT-5.4-mini   | 사용자 체감 속도가 핵심, 채점 4.1초 vs 10초 |

설정 파일(`application-{profile}.yml`)로 AI 모델 주입 → 코드 변경 없이 환경만 바꾸면 자동 전환

**남은 과제**: 현재 채점 4.1초도 절대적으로 빠르지 않음. 스트리밍 응답 방식으로 전환하면 첫 토큰 도착 시점부터 UI에 점진적으로 표시 가능 → 체감 속도 개선 여지 있음

### E. 파일 업로드 — S3 Presigned URL

**기존 방식**: 클라이언트 → 서버 → S3. 이미지 데이터가 서버의 메모리·네트워크 대역폭 모두 소모. 대용량 파일·동시 업로드 증가 시 서버가 병목

**개선 방식**: 클라이언트가 서버에 URL 발급 요청 → 서버가 S3 서명 임시 URL 반환 → 클라이언트가 S3에 직접 업로드
- 서버는 파일 데이터를 전혀 다루지 않아 CPU·메모리·대역폭 소모 없음
- 서명된 URL은 만료 시간이 있어 무단 업로드 방지

## 아키텍처 및 설계 원칙

| 원칙 | 설명 |
|------|------|

| Fallback | AI 장애 시 백업 문제 즉시 할당 — 서비스 가용성을 AI 의존성으로부터 격리 |
