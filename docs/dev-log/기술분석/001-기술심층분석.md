### [개선 과제 1] Async 스레드풀 고갈 위험

**현상**
- `ProblemGenerator.generateInitialProblem()`(신규 가입 시) + `SubmissionEventHandler`(제출 시)가 모두 같은 풀 사용
- 가입 버스트 + 동시 제출 폭주 시 queueCapacity=1,000 소진 → CallerRunsPolicy 발동 → HTTP 요청 스레드 블록
- AI 호출(평균 2~5초) + 이벤트 처리가 같은 풀을 경쟁 → 가벼운 이벤트(스트릭 업데이트)조차 지연

**개선 방안 — 목적별 스레드풀 분리**

```java
@Bean("aiTaskExecutor")
public Executor aiTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(5);
    executor.setMaxPoolSize(10);
    executor.setQueueCapacity(50);       // AI 작업은 큐를 짧게
    executor.setRejectionPolicy(new DiscardOldestPolicy());
    executor.setThreadNamePrefix("ai-async-");
    return executor;
}

@Bean("eventTaskExecutor")
public Executor eventTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(20);
    executor.setMaxPoolSize(50);
    executor.setQueueCapacity(500);
    executor.setThreadNamePrefix("event-async-");
    return executor;
}
```

```java
@Async("aiTaskExecutor")
public void generateInitialProblem(...) { ... }

@Async("eventTaskExecutor")
public void handleSubmissionCompleted(...) { ... }
```

### [개선 과제 2] Streak 낙관적 락 — 멱등성 보장 필요

**문제 시나리오**
1. 사용자가 제출 버튼을 2번 빠르게 클릭 → 두 @Async 핸들러가 동시에 `increaseWithRetry()` 호출
2. 스레드 A, B 모두 `version=1` 읽고 업데이트 시도
3. 스레드 B → `OptimisticLockException` → 재시도 → `version=2`로 성공 → **Streak이 2 증가**

**현재 구현**

```java
@Version
private Long version;

@Retryable(retryFor = {OptimisticLockException.class}, maxAttempts = 3, backoff = @Backoff(delay = 100))
public void increaseWithRetry(Long memberId) { ... }
```

재시도가 성공하면 결국 2 증가가 되므로 낙관적 락만으로는 부족하다. **멱등성 보장**이 우선이다.

**개선 방안 — Submission 단계에서 멱등성 체크**

```java
@Transactional
public void submitSolution(...) {
    if (submission.isStreakProcessed()) return;  // 이미 처리됨
    submission.markStreakProcessed();
    eventPublisher.publishEvent(new SubmissionCompletedEvent(memberId));
}
```

### [개선 과제 3] 스케줄러 — 대량 Update 비효율 + 분산 환경 중복 실행

**현재**

```java
@Scheduled(cron = "0 0 0 * * *")
public void initStreakWhoDidNotSubmitYesterday() {
    List<Long> memberIds = dailyProblemReader.findUnsolvedMemberIds(yesterday);
    memberIds.forEach(streakService::initStreak);  // 개별 UPDATE → N건 쿼리
}
```

**개선 방안 — 벌크 업데이트 + 청크 처리**

```java
@Modifying
@Query("UPDATE Streak s SET s.currentStreak = 0 WHERE s.member.id IN :memberIds")
void bulkResetStreak(List<Long> memberIds);

// 청크 처리 (OutOfMemory 방지)
for (int i = 0; i < memberIds.size(); i += CHUNK_SIZE) {
    streakRepository.bulkResetStreak(memberIds.subList(i, Math.min(i + CHUNK_SIZE, memberIds.size())));
}
```

**멀티 인스턴스 배포 시 — ShedLock 도입**

```java
@Scheduled(cron = "0 0 0 * * *")
@SchedulerLock(name = "streakReset", lockAtLeastFor = "PT5M", lockAtMostFor = "PT10M")
public void initStreakWhoDidNotSubmitYesterday() { ... }
```

### [잘 구현된 부분] MDC 컨텍스트 전파

```java
public Runnable decorate(Runnable runnable) {
    Map<String, String> contextMap = MDC.getCopyOfContextMap();
    return () -> {
        MDC.setContextMap(contextMap != null ? contextMap : Collections.emptyMap());
        try {
            runnable.run();
        } finally {
            MDC.clear();  // 스레드 반납 전 정리 → ThreadLocal 누수 방지
        }
    };
}
```

스레드 풀 재사용 시 이전 요청 컨텍스트 누수 방지까지 처리됨.

### [개선 과제 5] 캐시 — 수평 확장 시 인스턴스 간 불일치

**현재**: Caffeine (인메모리, 단일 인스턴스에 최적)

| 캐시명 | TTL | max | 용도 |
|--------|-----|-----|------|
| todayProblem | 자정까지 | 5,000 | 오늘의 문제 |
| streak | 30분 | 5,000 | 스트릭 조회 |
| dailyProblemDetail | 5분 | 15,000 | 문제 상세 |

**수평 확장 시 문제**: 인스턴스 A는 캐시 히트(stale), 인스턴스 B는 캐시 미스 → DB 조회로 데이터 불일치 가능

**개선 방향**: 단기는 Caffeine + TTL 조정 유지, 장기는 Redis 분산 캐시 전환

### [개선 과제 6] Circuit Breaker 미적용

**현재**: AI API 호출에 `@Retryable`만 적용 → 연속 실패 시 계속 재시도하며 스레드 소모

**개선 방안 — Resilience4j Circuit Breaker**

```java
@CircuitBreaker(name = "gemini", fallbackMethod = "fallbackGenerate")
@TimeLimiter(name = "gemini")
public CompletableFuture<ProblemResponse> generateProblem(String prompt) { ... }

public CompletableFuture<ProblemResponse> fallbackGenerate(String prompt, Exception ex) {
    return CompletableFuture.completedFuture(getBackupProblem());
}
```

```yaml
resilience4j:
  circuitbreaker:
    instances:
      gemini:
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        sliding-window-size: 10
  timelimiter:
    instances:
      gemini:
        timeout-duration: 10s
```

## 4. 보안 분석

### [개선 과제 7] Refresh Token Blacklist 없음

로그아웃 시 서버에서 refresh token 즉시 무효화 불가. 탈취된 토큰이 만료 전까지 유효하다.

**개선 방안 — Redis TTL 기반 블랙리스트**

```java
public void logout(Long memberId) {
    String refreshToken = memberReader.findById(memberId).getRefreshToken();
    long ttl = jwtProvider.getRemainingExpiry(refreshToken);
    redisTemplate.opsForValue().set("blacklist:" + refreshToken, "logout", ttl, TimeUnit.MILLISECONDS);
    memberManager.clearRefreshToken(memberId);
}

// JwtFilter에서 블랙리스트 체크
if (redisTemplate.hasKey("blacklist:" + token)) {
    throw new HaruHanaException(INVALID_TOKEN);
}
```
